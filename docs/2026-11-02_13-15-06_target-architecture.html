Telemetry flow

One reading, three paths

Hot path: alarms

Stream processor checks each reading against the alarm rule for its sensor type. A breach that lasts the rule's duration publishes AlarmRaised to the Service Bus topic. The worker keeps one active alarm per tower and sensor, so a flapping sensor does not open ten work orders.

Warm path: health and trends

Readings are rolled up to one row per sensor per minute and written to the database. The tower health page and 30-day trend charts read these rows; the API never queries raw telemetry.

Cold path: archive

IoT Hub routes every raw message to the Data Lake. Used for audits, model training and replaying history if an alarm rule changes. Nothing in the app reads it directly.

EscalatedWhen the work order is not completed by its SLA due time, a scheduled Service Bus message wakes the worker. It raises priority, notifies the regional manager and logs a WorkOrderEvent. The order stays with the same assignee unless reassigned.
CancelledFrom Open or Triaged only. Typical case: the alarm clears by itself before anyone is dispatched (for example mains returns). Cancelling needs a reason and is kept in the audit trail.
ReopenedIf verification fails because telemetry goes back over the threshold, the order returns to Assigned with the same history, so repeat faults are visible.

Business rules (proposed)

  • Status moves only along allowed transitions, enforced by a WorkOrderStateMachine in Domain; illegal move raises InvalidWorkOrderTransitionException (409).
  • Critical alarm opens a corrective work order automatically; Warning goes to a triage queue.
  • SLA due time comes from priority, held in configuration.
  • Check-in is accepted only near the site's latitude and longitude.
  • Closing needs verification: telemetry stable below the warning value for a configured period, or a supervisor sign-off.
  • If affected equipment is tenant-owned, or the alarm puts tenant service at risk, the tenant operators are notified.

Where it lives in the code

  • Domain: Monitoring/ and WorkOrders/ folders: entities, state machine, alarm evaluation rules (one class per rule, open for extension).
  • Application: IAlarmService, IWorkOrderService, INotificationSender, IWorkOrderDispatcher.
  • Infrastructure: EF configurations, Service Bus consumer as a hosted service, SignalR and email or webhook senders.
  • TowerCo.Ingestion (new): Azure Functions project for the stream processor, reusing Domain alarm rules.
  • Server: thin controllers and a SignalR hub. Same exception-to-ProblemDetails handler.

Decisions and open questions

What this design commits to

Modular monolithOne API, clear modules. Split into services only if load or team size needs it.
Event-driven ingestionTelemetry never hits the API directly in production; Service Bus decouples bursts from the app.
Rules in DomainAlarm and work order rules are plain classes, shared by the API and the Functions project, fully unit tested.
Telemetry storePer-minute roll-ups in Azure SQL, or Azure Data Explorer if sensor count grows. To decide.
Own or integrate work ordersBuild in-house as shown, or hand off to an existing maintenance system through an adapter. To decide.
Auto-open thresholdCritical only, or also repeated Warnings within a window. To decide with operations.
