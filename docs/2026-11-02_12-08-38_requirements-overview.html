Domain model

Six entities, capacity derived on read

One tower per site keeps Phase 1 simple. A tenancy is one operator holding one slot on one tower. Equipment sits on the tower and is always owned by a tenant. TowerCo's own power kit is site infrastructure, kept separate.

Derived capacity (never stored)

ActiveTenantCount = active tenancies on tower
AvailableSlots = MaxTenants − ActiveTenantCount
UtilisationPercent = ActiveTenantCount ÷ MaxTenants × 100
HasCapacity = AvailableSlots > 0

Calculated from tenancies each time, so it cannot drift out of sync. Structural load (wind, antenna weight) is a later extension.

Business rules when adding a tenant

  1. Site must be Active, else 409 SiteNotActive
  2. Operator not already active on this tower, else 409 DuplicateTenancy
  3. Tower has a free slot, else 409 TowerCapacityExceeded
  4. Unknown site, tower or operator: 404 NotFound

Architecture

Basic Clean Architecture, dependencies point inward

Business rules live in Domain and Application, away from EF Core and HTTP. Later controllers for UC1 and UC4 plug into the same layers.

Screens

  1. Sites list: country, status and text filters; tenants shown as x/y with capacity badge
  2. Site detail: site and tower info, capacity bar, tenancy table, equipment grouped by operator
  3. Add tenant form: operator, start date, monthly rent; disabled when tower is full

Seed data

4 countries (IN, ZA, KE, NG), about 12 sites with mixed statuses, about 5 fictional operators. Tenancies give a mix of full, partly used and empty towers so every rule can be shown. 8 equipment types; each tenancy has a radio and a microwave dish.

Out of scope

Create or edit site, map and dashboard, login and roles, ending a tenancy, Azure hosting, pagination.
