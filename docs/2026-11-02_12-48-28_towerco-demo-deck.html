Domain model

Six entities, capacity is derived

Every equipment item belongs to a tenant through its tenancy (for example a 5G antenna or microwave dish). TowerCo does not own equipment in this model. New equipment types are rows, not code.

Walk left to right. One tower per site is a deliberate simplification. Site location and rent are value objects (SiteLocation, Money), mapped as EF complex types. Capacity numbers are never stored, so they cannot drift from the tenancies.

Capacity model

Slots, counted from active tenancies

AvailableSlots = MaxTenants − active tenancies   Utilisation = active ÷ MaxTenants × 100. A tenancy is active when it has no end date or ends on or after today.

All domain exceptions go through one handler that returns RFC 7807 ProblemDetails, so the UI gets a clear message without per-controller code. Work orders add InvalidWorkOrderTransition (409) and assignee and title checks (400).

Telemetry
Proposed, not approved

One reading, three paths

Hot · seconds

Alarms. Alarm rules fire and publish to Service Bus.

One active alarm per tower and sensor, held in a Cosmos DB alarm-state item with an ETag check, so a flapping sensor does not flood the queue.

Warm · minutes to weeks

Raw readings and per-minute roll-ups in Azure Cosmos DB.

Partitioned by tower, then sensor, then day. Autoscale throughput, and a time to live from configuration keeps containers lean.

Cold · long term

Every raw reading in Data Lake, fed from the Cosmos DB change feed.

Audit, replay of new alarm rules over past data, and analytics.

Target: sensor data in Cosmos DB; business data (sites, tenancies, work orders) relational in SQLite now, Azure SQL later. Today: seeded sensor readings and inspections sit in a SQLite table and feed the tower health page. Thresholds come from configuration.

Why Cosmos DB for sensor data: write-heavy, append-only, read by tower and time range, and it must scale out as towers and sensors grow. A hierarchical partition key (tower, sensor, day) spreads writes and keeps "this tower, last 30 days" queries inside one partition prefix. Time to live removes old raw items automatically; the change feed copies everything to the data lake first. Throughput and retention values are configuration, not decided yet.
Sensor data collection
First slice builtRest proposed

Azure Functions in TowerCo.Ingestion

Built today: IoTHubIngestFunction (Event Hubs compatible trigger, bad messages logged and skipped) and HttpIngestFunction (POST /api/telemetry for the simulator or Postman, bad body returns 400). Both parse, check the reading against configured warning and critical thresholds, and publish an alarm; the publisher only logs for now.
Trigger
  • Azure IoT Hub, read through its Event Hubs compatible endpoint
  • Batches per partition, checkpointed, so a restart resumes where it stopped
  • Gateways enrolled through Device Provisioning Service with per-device certificates
Target pipeline, per batch
  1. Validate schema and units; bad messages go to a dead-letter container with the reason
  2. Enrich with tower and sensor from the sensor registry (cached)
  3. Store raw reading in Cosmos DB, keyed by message ID so a retry does not duplicate
  4. Roll up per tower, sensor and minute with a patch increment, so split or late batches still add up
  5. Evaluate alarm rules from Domain; a new or cleared alarm updates alarm-state and publishes to Service Bus
Outputs
  • Cosmos DB readings and rollups
  • Cosmos DB alarm-state
  • Service Bus tower-alarms
  • Dead-letter container
Archive function: Cosmos DB change feed trigger, writes every raw reading to Data Lake
Heartbeat function: timer; a gateway silent longer than the configured window raises "communication lost"
Simulator function: timer, sends readings for seeded towers such as IN-DEL-0002; demo only
Today two functions exist (IoT Hub and HTTP triggers) and share one processor that uses the Domain AlarmThreshold. Target: one ingestion app, four functions, each with one job. Scaling follows IoT Hub partitions, so more towers means more parallel batches without code changes. The function uses managed identity for Cosmos DB, Service Bus and Key Vault, so there are no connection secrets in config. Alarm rules are the same Domain classes the API uses, shipped as a shared library. Hosting plan is a Phase 7 choice: Flex Consumption or Premium if private networking is required.
Work order lifecycle
BuiltExtensions proposed

Six states, enforced in the domain

  • Raised against a site with category, priority and due date; starts Assigned if an engineer is given, otherwise Open.
  • An illegal move raises InvalidWorkOrderTransitionException (409); Assigned without an engineer returns 400.
  • Open work orders feed tower health: any Critical priority makes the tower critical.
  • Proposed next: auto-open from Critical alarms, triage, verification, SLA escalation from configuration, reopen on failed verification.
  • Example, seeded site IN-DEL-0002 Dwarka Sector 12 (Monopole 30 m, tenants Aurora Mobile and Bluewave Telecom): a shelter door contact opens with no technician checked in, so it raises an intrusion alarm.
This is the state machine in WorkOrder.cs today: a transition table in the entity, so the rule and its test sit together. Completed and Cancelled are final. The proposed extensions build on the same table, which is why adding a state is a small, testable change. The door example is part of the proposal, not built.

Design decisions

Choices and the reason for each

  • SQLite file database. Zero setup, created and seeded on first run, portable for a demo.
  • Derived capacity. Calculated from tenancies, never stored, so it cannot go stale.
  • Seed through domain methods. Demo data obeys the same invariants as live data.
  • Enums stored as text. The database reads clearly when inspected.
  • Equipment belongs to tenants. Each item hangs off a tenancy, so its owner is always an operator.
  • Custom exceptions to ProblemDetails. 404, 409 and 400 mapped in one place.
  • Typed mock API in the client. UI and backend were built in parallel; the UI now uses the real API, the mock stays behind one env flag.
  • Pinned packages. Upgrading to 10.0.14 cleared a high-severity Microsoft.OpenApi advisory.
Pick two or three of these depending on time. The mock API point explains how frontend and backend were built at the same time by separate streams.

Quality

How the code is kept honest

  • 153 xUnit tests: domain rules, work order transitions, health rules, Application services on seeded data, request validation, ingestion functions, persistence, exception mapping.
  • The progress log records 100% line and branch coverage on new hand-written code at each backend change; startup code and generated files excluded.
